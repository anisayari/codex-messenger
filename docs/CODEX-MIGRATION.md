# Migration Codex Messenger vers Codex CLI 0.156.1

Publication du 23 septembre 2026 : Messenger **v0.0.3** exige Codex **0.156.1**, dernière stable vérifiée dans npm et GitHub. Le hotfix ajoute Sol/Luna au catalogue dynamique ; les 746 JSON standard/expérimentaux sont identiques octet par octet à 0.156.0. L’archive comprend maintenant 51 releases. Voir [le delta 0.156.1](CODEX-0.156.1-DELTA.md) et [la validation de publication](PUBLICATION-0.0.3.md). Les résultats datés ci-dessous conservent leur version réellement testée.

Référence vérifiée le **22 septembre 2026** : le projet annonçait un minimum de CLI **0.125.0**, le binaire local était **0.154.0**, et `dist-tags.latest` du [registre npm officiel](https://registry.npmjs.org/@openai%2fcodex) donne **0.156.0**. L'[archive complète](codex-changelog/README.md) contient les 50 versions stables publiées de `0.125.0` à `0.156.0`, sans changelog manquant dans cet ensemble. Les numéros `0.126.0` et `0.127.0` ne sont pas des versions npm stables publiées.

La version stable **0.156.0** a été publiée pendant ce travail. Ses archives npm wrapper et darwin-arm64 ont été vérifiées contre SHA512 et SHA1 npm, son binaire confirme `codex-cli 0.156.0`, et ses schémas standard/expérimentaux ont été générés. Le delta retire `thread/rollback`, ajoute l’expérimental `rollout/compress`, expose les capacités annoncées des serveurs MCP et conserve le contrat `account/usage/read`. Voir [CODEX-0.156.0-DELTA.md](CODEX-0.156.0-DELTA.md).

Ce document conserve l’inventaire des releases et du protocole, puis décrit la couverture implémentée et ses preuves. L’inventaire détaillé reste une référence de contrat ; il ne constitue pas une déclaration de parité totale avec chaque produit Codex ou chaque compte.

## Contrat réellement disponible

Le binaire npm `0.155.1` a généré son protocole avec `codex app-server generate-json-schema`, puis avec `--experimental`. L'[inventaire daté](codex-changelog/protocol-methods-0.155.1.json) conserve les méthodes et empreintes des deux ensembles. L'ensemble avec opt-in expose **164 méthodes de requêtes clientes**. Les méthodes de test, comme `mock/experimentalMethod`, et les mécanismes réservés à des hôtes ne sont pas des fonctions à ajouter dans une interface utilisateur.

`initialize.capabilities.experimentalApi = true` rend le client éligible aux champs et méthodes expérimentaux. Ce drapeau ne crée pas une capacité manquante : modèle, compte, plateforme, configuration, transport et hôte peuvent encore refuser une opération. Une erreur de capacité doit rester visible avec la réponse du serveur, sans succès simulé. Les schémas sont générés par la version installée ; une liste statique de modèles ou de champs du protocole de 2026 ne doit pas devenir une promesse pour les versions futures.

Le [changelog produit officiel](https://learn.chatgpt.com/docs/changelog) distingue CLI, produit desktop et annonces de modèles. Il précise que `codex app-server` est expérimental. Le client MSN peut intégrer son protocole ; il ne peut pas déduire d'une release desktop une API publique équivalente.

La lecture paginée exige aussi un stockage compatible : le [code officiel 0.155.1](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/thread-store/src/local/thread_history/read.rs) refuse `list_turns` si la base d’état est absente, si la ligne de métadonnées du thread n’est pas encore matérialisée, ou si son historique est legacy. Des tests réels dans un `CODEX_HOME` isolé et sans compte ont reçu, sur un nouveau thread sans tour, `-32601 / list_turns is not supported yet` puis `-32600 / is not materialized yet; thread/turns/list is unavailable before first user message`. La lecture des métadonnées fonctionne. Ces refus ne démontrent pas que tous les historiques persistés sont indisponibles. L’interface doit distinguer historique vide, encore non matérialisé et fonction indisponible, puis conserver les métadonnées et une raison lisible.

Les 31 tests ciblés des services publics couvrent catalogues, compte, crédits, file, mémoire, recherche, compactage, retrait historique, usage et capabilities MCP. Les CRUD de file n’ont pas été exécutés contre un compte externe : leurs fixtures et la lecture sur CLI isolé sont des preuves différentes. Le dispatch à vide est vérifié par les [tests officiels 0.155.1](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/app-server/tests/suite/v2/thread_queue.rs).

La recherche d’occurrences exige un stockage paginé compatible ; le [stockage officiel 0.155.1](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/thread-store/src/local/thread_history/search.rs) valide ce prérequis avant de parcourir les messages visibles. Son refus dans un profil neuf sans tour ne prouve pas une indisponibilité générale pour les conversations matérialisées. Le panneau affiche la raison du serveur et conserve la recherche locale existante.

Le [contrat officiel de gestion des conversations](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/app-server/src/request_processors/thread_processor.rs) dépréciait rollback pour les historiques legacy ; 0.156.0 retire cette méthode et les conversations paginées utilisent uniquement revert. Messenger limite ce contrôle au dernier tour contenant un message utilisateur, vérifie un identifiant attendu et exige une confirmation après consultation de l’aperçu. Il n’affiche pas « annuler les fichiers ». Le contrôle d’inactivité est une lecture fraîche, pas une transaction atomique avec des clients externes concurrents ; un autre client peut modifier la conversation entre cette lecture et l’action.

Une fixture CLI **0.156.0 réellement authentifiée** a effectué une seule inférence bénigne `CODEX-MSN-OK`, puis validé l’historique complet matérialisé, resume, fork, recherche et deux occurrences dont les bornes UTF-16 sont valides. Le profil/processus temporaires ont été supprimés (zéro restant). Cette preuve ne valide pas un appel vocal, un microphone matériel, un crédit ou l’usage facturé. Log local de validation : `/tmp/codex-messenger-authenticated-01560-live.log`.

## Surfaces publiques d’administration et mécanismes internes

Les RPC `remoteControl/*`, `environment/*`, `memory/status/reset` et `thread/memoryMode/set` sont des méthodes **publiques expérimentales**. Leur absence d’un bouton n’en fait pas une API privée. RemoteControl configure l’installation et peut être refusé sans RemoteControlHandle ou par la politique ; environment/add enregistre/remplace un exécuteur et ne sélectionne pas à lui seul cet environnement pour un chat. Voir les processeurs officiels [remote control](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/app-server/src/request_processors/remote_control_processor.rs) et [environment](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/app-server/src/request_processors/environment_processor.rs).

Les véritables limites internes/test sont les tokens `chatgptAuthTokens` marqués « INTERNAL USE ONLY », l’injection d’historique Cloud brut dans resume, experimentalRawEvents, mock/experimentalMethod et les champs mock. L’auth ChatGPT ordinaire et les approbations publiques fonctionnent sans les imiter. Attestations, challenges signés et décisions Guardian administratives sont des contrats d’hôte : une fenêtre de chat ne peut pas produire une preuve native ou une identité distante fictive.

## Changements de produit hors numéros CLI

Les annonces du [changelog officiel](https://learn.chatgpt.com/docs/changelog), vérifié le 22 septembre 2026, ajoutent trois points de migration qui ne doivent pas devenir des constantes arbitraires :

- **GPT-6 Sol et Luna**, annoncés le 22 septembre, sont en rollout et dépendent du compte/workspace. La liste retournée par `model/list` reste l'autorité pour l'interface ; ajouter ces noms à une liste locale ne les rend pas disponibles.
- **GPT-5.3-Codex-Spark** est déprécié depuis le 14 septembre. **GPT-5.5** a une retraite annoncée pour le 14 octobre dans ChatGPT/Work/Codex ; l'annonce précise que cela ne retire pas le modèle de l'API OpenAI. Le client doit traiter les choix sauvegardés devenus indisponibles et permettre un choix courant.
- **`codex mcp-server`** et son binaire standalone ont été supprimés après dépréciation. Codex Messenger utilise déjà `codex app-server` ; garder cette intégration, tout en conservant la connexion de Codex aux serveurs MCP externes via `codex mcp`.

Les capacités desktop/browser/computer-use, cloud, connecteurs gérés, notifications mobiles et automations d'un produit OpenAI ne sont pas toutes des APIs publiques de ce binaire. Toute exposition dans Messenger nécessite une capacité véritablement fournie et testée par son hôte. L'interface ne doit pas afficher une imitation comme une intégration fonctionnelle.

## Éléments MSN et périmètre honnête

La liste de contacts/groupes, les fenêtres de conversation, avatars et statuts, emoticônes, clin d'œil, wizz, thème, sons, historique, envoi de fichiers/images et invitation audio ont des analogues authentiques dans Messenger. Ils peuvent habiller les fonctions réelles ci-dessus. Un wizz ou un clin d'œil local reste une animation locale si aucun protocole de pair distant ne le transmet ; sa présentation doit l'indiquer. Un agent « occupé » correspond à un tour actif, « action requise » à une requête serveur, et « hors ligne » à un service réellement indisponible.

Les appels audio/vidéo entre humains, contacts MSN Live, SMS, jeux, partage de dossiers ou de musique ne deviennent pas disponibles en changeant l'apparence de Codex. Les assets historiques manquants demandent un audit distinct d'origine et d'usage ; cette migration du runtime ne constitue pas une autorisation ni une preuve de disponibilité de ces assets.

## Vérification de la migration

Le 22 septembre 2026, [le test authentifié opt-in](../tests/codexAuthenticatedLive.test.mjs) a réussi sur le vrai CLI/app-server 0.155.1 avec le modèle par défaut : un tour a répondu exactement `CODEX-MSN-OK` en six deltas, sans activité d'outil observée. Après arrêt et redémarrage du serveur, `thread/read` avec tous les tours et `thread/turns/list` ont retrouvé cette réponse. `thread/resume` avec les tours et `thread/fork`, puis la lecture complète du fork, ont conservé son historique réel. Le test s'est terminé en moins de 60 secondes et les répertoires temporaires ont été effacés. Les diagnostics enregistrent uniquement méthodes, IDs, nombres d'événements, statut et cette réponse fictive ; aucun compte, jeton ou paramètre privé.

Cette preuve valide l'inférence, le streaming et la persistance du serveur pour cette fixture et cette connexion CLI. Elle ne remplace pas les vérifications visuelles Electron ni la validation de toutes les fonctions sur tous les comptes/providers.

La même fixture authentifiée, relancée après les corrections finales du client, a aussi validé `thread/search` sur son propre thread matérialisé et `thread/searchOccurrences` : deux occurrences réelles ont été retournées, avec les bons IDs et des plages UTF-16 sélectionnant exactement `CODEX-MSN-OK`. Relecture après redémarrage, reprise et fork ont de nouveau réussi. Cette passe a utilisé une seule génération, s'est terminée en moins de dix secondes et a effacé ses données temporaires ; aucun historique personnel n'a été copié ni affiché.

La validation doit distinguer trois preuves : **schéma authentique** pour méthode/params, **serveur réel** pour handshake/catalogues/historique et comportement RPC, **interface Electron** pour interaction pratique. Des fixtures de protocoles doivent couvrir les demandes interactives et les cas de réseau difficiles sans consommer de crédits, supprimer de conversations personnelles ou exécuter d'actions dangereuses.

Les scénarios indispensables sont connexion/reconnexion, envoi et streaming, reprise/fork/historique paginé, modèles/efforts, Queue/Steer/Stop, approvals/questions/MCP, fichiers/images, terminal, objectifs, catalogues et états de compte. Une fonction avec seulement une fixture est couverte au niveau du contrat, pas validée sur tous les comptes/providers. Une fonction gated ou absente doit être indiquée telle quelle ; « toutes les features » ne peut pas être déduit d'un build qui passe.

Les chemins de code, résultats de tests et limites observées sont consignés dans VALIDATION.md, les audits et la matrice de couverture ci-dessus. L’inventaire du protocole décrit les fonctions publiées ; leur présence seule ne vaut ni intégration ni validation sur le compte utilisateur.
