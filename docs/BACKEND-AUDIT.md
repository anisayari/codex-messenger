## Couverture observée et limites

Les tests initiaux existants passent (21/21), mais couvrent principalement les utilitaires purs, métadonnées de release et un serveur JSON-RPC simulé. Ils ne démontrent pas les permissions caméra/micro, une signature Windows, un téléchargement réel, l'installation d'un paquet, une approbation sensible ou les actions de plusieurs fenêtres en conditions réelles. Plusieurs lectures initiales du disque ont pris des dizaines de secondes ; la durée de 197 secondes du test initial ne correspond pas à une latence applicative démontrée.

Les nouveaux tests `backendReliability.test.mjs` utilisent des fichiers temporaires, des réponses réseau simulées et un script d'installation exécuté avec commandes de signature/montage simulées. Ils vérifient les transactions, le rejet des origines IPC, l'intégrité du téléchargement et la restauration après échec sans remplacer une application utilisateur. Une signature authentique et une publication notarisée doivent encore être validées sur les artefacts de release avant de promettre une installation automatique sur tous les postes.

## Améliorations de maintenance

`main.js` mélange paramètres, profils, protocole, historique, contacts, fenêtres, médias et handlers dans plus de 3 000 lignes. Extraire progressivement les transactions de paramètres, la validation des entrées, les files d'envoi et les handlers de médias permet de les tester sans démarrer Electron. Garder un registre de capacités réelles du serveur pour désactiver honnêtement les commandes absentes d'une version, et éviter de représenter les agents Codex comme des correspondants humains connectés. Les notifications synchronisent les images sur le thread principal ; une petite cache d'assets et un décodage d'image borné éviteraient des blocages sur des fichiers arbitraires.

## Vérification du serveur actuel

Le CLI local `codex-cli 0.155.1` a été interrogé dans un profil temporaire sans compte et sous sandbox macOS interdisant le réseau. Les catalogues modèles, activités, applications, connecteurs MCP, modes de collaboration, exigences et profils de permissions répondent réellement ; les quotas restent indisponibles sans compte, état affiché explicitement. Le nouveau terminal utilise exclusivement `command/exec` avec une session PTY, contrôle de fenêtre propriétaire, lecture UTF-8 incrémentale, stdin, redimensionnement et terminaison. Les sept tests dédiés passent. Un `printf` réel a été exécuté via ce serveur sous politique explicitement externe, correspondant au sandbox réseau externe du test : sortie attendue et code 0. Une politique lecture seule imbriquée dans ce même sandbox externe retourne le code macOS 71 ; elle n’a jamais été réessayée automatiquement avec des permissions plus larges dans l’application.

Le terminal fournit un transcript texte borné (60 secondes et 4 Mo par flux). Il ne prétend pas être un émulateur ANSI pour applications plein écran. Le test opt-in `codexFeatureLive.test.mjs` conserve un compte temporaire et ne lance aucun tour modèle.


## Vérifications complémentaires — 22 septembre 2026

- La journalisation de démarrage est facultative : une erreur `ENOSPC` produit uniquement un code d’erreur borné et laisse démarrer la fenêtre et l’icône système. Le test exécute le vrai callback de démarrage avec cette panne injectée.
- L’arrêt explicite du serveur émet désormais `status: stopped` après avoir effacé les RPC en attente, les conversations chargées et les métadonnées de connexion. Le callback principal expire les demandes du serveur, les autorisations et les tours actifs. Le test réutilise un identifiant RPC après redémarrage et prouve qu’une réponse tardive à l’ancienne demande ne répond jamais à la nouvelle.
- Les événements publics de conversation conservent les identifiants de thread et de tour, le parent immédiat et les ancêtres dérivés du registre (au plus 64, sans cycle). Un sous-agent ne termine pas le tour ni la notification de fin de son parent ; un thread enfant ouvert comme conversation indépendante reçoit sa propre fin. `phase`, `delivery`, `questions` et `memoryCitation` sont les seuls champs supplémentaires conservés pour les messages assistant, conformément au schéma officiel 0.156.0, sans transfert d’objet brut ni raisonnement privé.
- Le seul sous-frame permis est le document local exact `msn-assets/flash-player/index.html`. Son lecteur utilise le protocole local `msn-asset://local/`, limité à 19 SWF MSN et aux cinq fichiers du runtime Ruffle 0.6.0. Le handler refuse les autres routes, méthodes, identifiants, traversées, liens symboliques sortants et fichiers trop volumineux ; il n’active aucun contournement de CSP. Le frame reste sans API preload ni Node.
- Le diagnostic natif a détecté puis corrigé deux erreurs invisibles en HTTP : Chromium ignore les sources CSP écrites comme chemins `file://`, et `location.origin` vaut `file://` alors que les messages du frame portent l’origine sérialisée `null`. Le protocole restreint corrige la première ; la vérification du WindowProxy, du jeton et de l’origine propre au mode fichier corrige la seconde.
- Les dix-sept nouvelles régressions démarrage/arrêt/navigation/protocole/sous-agents/mode collaboratif passent avec Node natif contre les octets du snapshot attesté. Les exécutions bloquées sur des fichiers iCloud ne sont jamais comptées comme réussites.
- Le capstone réel Electron 41.10.7 valide : preload/bootstrap et API terminal disponibles, isolation Node conservée, vrai `heart.swf` chargé (125×118), volume 0→1→0 puis lecteur détruit. Le SWF et les deux WASM exacts répondent 200 ; une requête HTTPS distante et un autre PNG local sont bloqués par `connect-src`. Aucune erreur JavaScript, CSP normale, preload ou processus renderer n’est signalée avant les deux sondes négatives attendues. Le profil Chromium et `CODEX_HOME` sont temporaires et privés ; les profils usuels restent inchangés.

Le mode collaboratif renvoyé par `thread/resume` 0.156.0 est observé dans une map runtime indépendante par thread, copié sans instructions développeur et remis à zéro à l’arrêt ou lorsqu’un ancien serveur omet cette réponse. L’UI reçoit cette observation séparément des choix utilisateur : aucune sélection Auto ni configuration de projet n’est remplacée. Cinq régressions prouvent ces propriétés, les deux contrats preload de préférences vocales et le rejet d’une reprise résolue juste avant l’arrêt : son ancien état ne peut pas réapparaître après le redémarrage.
